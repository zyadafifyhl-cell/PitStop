1. Executive overview & platform roles

1.1 Platform purpose

PitStop is a multi-tenant marketplace for automotive services and retail in Egypt. One Expo app serves three distinct populations from a shared Supabase project:

Population Primary job Typical entry
Customers Discover shops, book services, buy parts/accessories, track orders /welcome → customer login or guest → /(tabs)
Merchants / owners Operate a shop: queue, catalog, inventory, fulfillment, settings /welcome?focus=owner → /(tabs)/shop
Super admins Approve merchants, toggle premium, moderate content, remove accounts Owner login with users.role = admin → /admin

The domain is shop-centric: every merchant brand is a row in public.shops. Physical locations are public.shop_branches. Customers never own shops; they own bookings, carts, orders, vehicles, and community posts.

1.2 Multi-tenant domain model

Tenancy is shop_id scoped, not organization-id scoped.

auth.users (Supabase Auth identity)
    │ 1:1  (handle_new_auth_user trigger)
    ▼
public.users  role, shop_id, branch_id, is_active
    │
    ├── customer          → no shop_id
    ├── pending_owner     → shop_id set, shop.is_active = false
    ├── owner             → shop_id required
    ├── branch_manager    → shop_id + branch_id required
    └── admin             → no shop_id

public.shops  (tenant root)
    ├── shop_branches     (physical bays / locations)
    │     ├── branch_services
    │     └── branch_employees   (no login)
    ├── products          (parts / accessories merchants)
    ├── store_orders
    ├── bookings
    ├── shop_extras       (JSONB profile, hours, gallery)
    ├── offers / coupons / campaigns
    └── shop_push_tokens

1.3 Role definitions

App identity lives in public.users. TypeScript mirror: lib/supabase/database.types.ts → DbUserRole.

Role Login context Session resolver Can do Cannot do
customer CustomerAuthContext Confirmed auth.users email that is not a shop staff email Browse, book, cart, checkout, reviews, community Open merchant dashboard
Guest continueAsGuest() Local flag only, no auth.uid() Browse catalog / map Checkout, booking persist, cart persist
pending_owner ShopAuthContext.login resolveShopSession Wait after register Operate dashboard (pending_approval)
owner ShopAuthContext users.role=owner + shop_id Full shop + all branches (premium for extra branches) Admin approval RPCs
branch_manager ShopAuthContext users.role=branch_manager + branch_id Queue, walk-in POS, branch-scoped bookings Other branches, premium toggles, delete shop
admin Same merchant login form users.role=admin Approval, premium, moderation, merchant delete Impersonate customer checkout

Staff vs customer isolation

  • CustomerAuthContext.resolveCustomerFromUser rejects emails that isShopStaffEmailRemote reports as shop staff.
  • ShopAuthContext.login returns shop_not_found if the session is not owner/manager/admin/pending_owner.
  • Admins are redirected: app/(tabs)/shop.tsx → router.replace('/admin').

Customer register: CustomerAuthContext.register → auth.signUp → handle_new_auth_user inserts public.users with role='customer'.

Merchant register: lib/shop/ownerRegistrationRepository.ts → auth.signUp (metadata account_type=shop_owner) → RPC register_shop_owner(...) creates an inactive shop and sets users.role='pending_owner'. Login then returns pending_approval until a super admin accepts.

Password reset: /reset-password (customers). Merchant password change: /shop/merchant-password.

Account deletion: customers call deleteCustomerAccountRemote (lib/account/customerAccountRepository.ts); merchants are removed only by admin (deleteMerchant).

  2. Validate offer (validateOfferForBooking) — percentage, flat, BOGO, buy-X-get-Y.
  3. Optional coupon (validateCouponForCheckout + registerCouponUsageRemote; rolls back booking if usage log fails).
  4. Optional loyalty (validatePointsRedemptionRemote / deductMerchantLoyaltyPointsRemote).
  5. Platform fee = 12% of net (PLATFORM_FEE_RATE in lib/booking/offerPricing.ts).
  6. Insert booking; wash shops attach default branch_id if missing.

Slot collision is enforced by occupancy in buildSlotsForShopDate (client) plus merchant queue; stock of time is the slot, not a row lock.

3.4 Atomic store checkout (place_store_order)

Security definer RPC. Canonical body: supabase/store_enhancements_production.sql (also mirrored in complete_system_schema.sql). Client: lib/store/productRepository.ts placeStoreOrder. Signature includes optional p_shop_id so a mixed cart can check out one merchant at a time.

BEGIN  (implicit in PL/pgSQL function)

1. AUTH
   auth.uid() IS NOT NULL
   else raise 'Not authenticated'

2. CART SHAPE
   optional p_shop_id filters cart lines to that merchant
   lock products FOR UPDATE (ordered by product id)
   cart not empty
   all products active and have shop_id
   DISTINCT shop_id count = 1
   that shop is_active

3. STOCK CHECK
   for each cart line:
     if products.stock_quantity < cart.quantity
        raise 'Insufficient stock for product %'

4. PRICE
   unit = coalesce(sale_price, price)
   subtotal = Σ unit * qty
   total = subtotal + delivery_fee

5. ORDER INSERT  status='pending'
   store_orders (user_id, shop_id, customer_*, fulfillment, payment_method, totals)

6. LINES + STOCK RESERVE (decrement)
   insert store_order_items
   update products set stock_quantity = stock_quantity - qty
     where stock_quantity >= qty
   if not found → raise (concurrent checkout lost the race)

7. CLEAR CART
   delete cart_items where user_id = auth.uid()

8. RETURN order uuid

END

Reservation model: there is no separate reservations table. Stock is decremented at order insert. Cancellation does restock atomically: owner update_store_order_status(..., cancelled) and customer cancel_own_store_order lock product rows and increment stock_quantity by each line qty.

Single-merchant rule: mixed-shop carts fail with Checkout supports products from one merchant at a time unless the client passes p_shop_id and only that shop’s lines are checked out.

5.5 RLS security model

RLS is enabled on shops, products, cart, orders, order items, bookings, extras, and related social tables.

Cart (cart_items): select/insert/update/delete only when auth.uid() = user_id.

Products:

  • SELECT if is_active OR admin OR is_shop_owner(shop_id)
  • INSERT/UPDATE/DELETE: admin or owning merchant (unify-store-owner-data-access.sql / complete_system_schema.sql)

Store orders:

  • SELECT: buyer (user_id) OR admin OR shop owner
  • UPDATE: admin or shop owner (status workflow via RPC, not a raw client UPDATE)
  • INSERT: not granted to clients; only place_store_order (security definer)
  • Customer cancel: only via cancel_own_store_order (pending + buyer + restock)

Order items: SELECT if parent order is readable by the same rules.

Bookings:

  • INSERT: open (Anyone can create bookings) so guests-turned-customers and walk-in POS can write
  • SELECT: customer_id = auth.uid() plus owner/manager policies from shop RLS (can_manage_shop / branch filters in later steps)
  • Customer UPDATE: only to cancelled
  • Owner UPDATE: status + rejection note via authenticated owner policies in schema.sql / step 2–4

Shop extras: public SELECT; mutating requires admin or owner.

Users: self-read plus is_platform_admin().

Shops: public catalog read for active shops; admin read-all; owner manage own.

Policies are defense in depth. Stock mutation during checkout is not done with a client UPDATE; it is inside the RPC.

Appendix C — Operational notes for implementers

  1. Do not insert store_orders from the client. Always rpc('place_store_order').
  2. Do not decrement or restock stock in the app. Checkout and cancel RPCs row-lock products (FOR UPDATE).
  3. Cart checkout is single-shop. Pass p_shop_id to check out one merchant from a mixed cart.
  4. SKU media is multi-image. Cover image_url plus image_urls (max 5). Shop/branch galleries remain separate JSON arrays.
  5. Revenue is completed-only. Pending / preparing / ready are operational, not GMV.
  6. Cancel restocks. Owner cancel at any non-cancelled status, and customer cancel while pending, both increment stock.
  7. Customer store orders live on /(tabs)/orders, not on the bookings tab.
  8. Delivery zones are not modeled. COD uses a customer-typed address and a flat 50 EGP fee. Pickup delivery line is Free / مجاناً on the tax invoice.
  9. “Bays” = shop_branches + slot occupancy, not a separate bay entity.
  10. Premium is the main merchant feature flag (shops.is_premium), toggled only by admins.
  11. Realtime requires replica identity FULL on store_orders, bookings, and products for complete row payloads.
  12. Virtual done is display-only until an owner persists status; do not book revenue on lifecycleAutoCompleted.
  13. Admin delete is destructive and confirmation-gated in UI; bookings cascade with the shop.
